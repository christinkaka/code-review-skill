# Subagent 委派评审架构

## 架构概述

用户通过 TRAE Agent 聊天窗口触发代码评审，主 agent 执行确定性扫描后委派子 agent 进行代码评审，最终汇总评定决策。

```
┌─────────────────────────────────────────────────────────────┐
│  用户在 Agent 聊天窗口触发                                    │
│  例如："帮我扫描一下这个仓库的安全问题"                       │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  主 Agent 识别意图                                           │
│  ├─ 解析用户提示词                                           │
│  ├─ 选择工作流（security/quality/performance/architecture） │
│  └─ 确定扫描参数                                             │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  主 Agent 执行 scan.py（确定性扫描）                         │
│  ├─ Git diff 分析                                            │
│  ├─ 调用图构建                                               │
│  ├─ 规则引擎扫描（Semgrep）                                  │
│  └─ 生成扫描结果文件                                         │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  主 Agent 委派子 Agent 进行代码评审                          │
│  ├─ 传递扫描结果文件路径                                     │
│  ├─ 指定工作流和温度参数                                     │
│  ├─ 单评审员（默认）：委派 1 个子 Agent                      │
│  └─ 投票模式（voting.votes > 1）：并行委派 N 个独立子 Agent  │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  子 Agent 执行代码评审                                       │
│  ├─ 读取扫描结果文件（subagent-review-task.md）              │
│  ├─ 分析代码上下文                                           │
│  ├─ 过滤误报（低温度参数 0.1-0.2）                           │
│  ├─ 生成修复建议                                             │
│  └─ 单评审员写 ai-review-result.json                        │
│     投票模式各写 ai-review-result-vote{N}.json（互不参考）   │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  主 Agent 汇总评定决策                                       │
│  ├─ 单评审员：直接合并评审结果                               │
│  ├─ 投票模式：多数票聚合（≥ votes//2+1 票，见下文）          │
│  ├─ 生成最终评审报告                                         │
│  ├─ 统计摘要（问题分布、严重程度）                           │
│  └─ 输出给用户                                               │
└─────────────────────────────────────────────────────────────┘
```

## 完整工作流程

### Step 1: 用户触发

用户在 TRAE Agent 聊天窗口输入提示词：

```
帮我扫描一下 release/1.0 分支和 master 分支的代码差异，看看有没有安全问题
```

或

```
对当前仓库执行代码评审，使用严格模式
```

或

```
检查一下这个 PR 有没有安全漏洞
```

### Step 2: 主 Agent 识别意图

主 Agent 解析用户提示词，确定：
- **工作流**：security / quality / performance / architecture / comprehensive
- **扫描模式**：diff 模式 / full-scan 模式
- **Profile**：default / strict / minimal

### Step 3: 主 Agent 执行确定性扫描

主 Agent 调用 scan.py：

```bash
python scripts/scan.py \
  --repo /path/to/repo \
  --base master \
  --target release/1.0 \
  --profile default \
  --workflow security \
  --output report/
```

生成扫描结果文件：
- `report/report.json` - 结构化扫描结果
- `report/report.md` - 可读的扫描报告
- `report/summary.json` - 统计摘要

### Step 4: 主 Agent 委派子 Agent

主 Agent 委派子 Agent 执行代码评审任务：

```
请对以下代码扫描结果进行评审：

## 工作流
安全审计工作流

## 温度参数
temperature: 0.1

## 扫描结果
读取文件：report/report.json

## 评审要求
1. 分析每个问题的真实性（排除误报）
2. 评估问题的严重程度（0-1 之间的置信度）
3. 为真实问题生成具体的修复建议
4. 使用严谨的评审标准（温度 0.1）

## 输出格式
返回 JSON 格式的评审结果，包含：
- rule_id: 规则 ID
- is_valid: 是否为真实问题
- confidence: 置信度（0-1）
- enhanced_fix: 修复建议
- analysis: 分析说明
```

#### 投票模式的委派差异（voting.votes > 1）

任务文件（`subagent-review-task.md`）自动注入"投票委派要求"段，主 Agent 按契约**并行委派 N 个相互独立的子 Agent** 评审同一份任务文件：

1. N 个评审员使用相同的评审契约（任务文件 + ai-enhancer-prompt.md）
2. 各自将结果写入独立文件：`ai-review-result-vote1.json` ~ `ai-review-result-vote{N}.json`
3. 评审员之间不得共享结论或互相参考（保证票间独立性，Self-Consistency 的前提）
4. 全部 N 份结果就绪后，`scan.py::_merge_subagent_review` 按 (rule_id, file, line) 多数票聚合

### Step 5: 子 Agent 执行评审

子 Agent：
1. 读取 `report/report.json`
2. 分析每个问题的真实性
3. 评估置信度
4. 生成修复建议
5. 返回结构化评审结果

### Step 6: 主 Agent 汇总评定决策

主 Agent（或重跑 `scan.py` 触发 `_merge_subagent_review`）：
1. 接收子 Agent 评审结果（单评审员 1 份 / 投票模式 N 份）
2. 投票模式先做多数票聚合（见下节），单评审员直接合并
3. 生成最终评审报告（多数票判误报的条目被滤除）
4. 统计问题分布和严重程度
5. 输出给用户

## 多评审员投票机制（多数票聚合）

### 设计动机

单次 LLM 裁决存在采样方差——同一条问题两次评审可能一次保留一次过滤。投票机制（Self-Consistency，Wang et al. 2022）把"随机波动"滤掉，只留下"稳定判断"：N 个相互独立的子 Agent 评审同一批问题，多数票决定去留。

### 聚合规则（`scan.py::_aggregate_votes`）

```
majority = votes // 2 + 1        （3 票需 ≥ 2 票）

对每条问题（键 = rule_id + file + line）：
  FP 票 ≥ majority  → 滤除（多数票认定误报）
  TP 票 ≥ majority  → 保留，字段取 TP 票中 ai_confidence 最高者，
                      并标注 vote="TP {n}/{votes}"
  无多数（平票/三向分歧/评审员覆盖不一致）
                    → 保守保留，needs_review=true，转人工复核
```

**与 API 路径平票语义的差异**：API 路径（`AIReviewer._review_with_voting`）平票时全丢弃；子 Agent 路径平票时**保守保留**。理由：子 Agent 路径覆盖 WARNING/INFO 低级别问题，且对安全工具而言，漏报 CRITICAL 的代价高于多一条待人工复核的告警。

### 边界行为

| 场景 | 行为 |
|------|------|
| 某评审员未覆盖某条问题（缺席） | 该票不计入分母，达不到多数时保守保留 |
| 某份投票文件损坏/非法 JSON | 该票跳过（warning 日志），其余票继续聚合 |
| 全部判误报（ai_results 为空） | dropped_keys 仍生效，全部滤除 |
| votes=1（默认） | 投票关闭，走单评审员合并路径（旧文件 ai-review-result.json） |
| 偶数票（votes=2） | 平票概率高，建议配置奇数票（3/5） |

### 真实验证（2026-08-26，WebGoat 22 条）

3 个独立子 Agent（qwen-3.7-plus）背靠背评审同一任务文件：

- **票间完全一致率 90.9%**（20/22 条三票同判）
- 2 条分歧项均被多数票正确裁决：`api-java-missing-validation`（TP/FP/TP → 保留）、`err-java-empty-catch`（FP/TP/FP → 滤除）
- 最终 22 条 → 4 条（3 条 3/3 全票 + 1 条 2/3 多数票），详录见 `reports/real-agent-validation-2026-08-26.md`

## 温度参数配置

为确保代码审核的严谨性和评价的一致性，子 Agent 使用以下温度参数：

| 工作流 | 温度 | 说明 |
|--------|------|------|
| security | 0.1 | 安全审计需要最高严谨性 |
| quality | 0.2 | 代码质量评审需要较高一致性 |
| performance | 0.1 | 性能分析需要严谨性 |
| architecture | 0.2 | 架构评审需要一致性 |
| comprehensive | 0.1 | 综合评审需要严谨性 |

**低温度参数的优势**：
- **严谨性**：减少随机性，确保评审结果稳定
- **一致性**：相同代码在不同时间评审结果一致
- **准确性**：减少幻觉，提高问题识别准确率

## 优势

### 1. 清晰的职责分离
- **主 Agent**：负责流程编排和结果汇总
- **子 Agent**：专注于代码评审
- **Python 脚本**：负责确定性扫描

### 2. 无需外部 API
- 完全离线可用
- 无需配置 LLM API
- 降低成本

### 3. 严谨性和一致性
- 低温度参数确保评审稳定
- 相同代码评审结果一致
- 减少误报和漏报

### 4. 灵活性
- 可以根据需要委派不同的子 Agent
- 可以并行处理多个评审任务
- 可以自定义评审标准

### 5. 可追溯性
- 所有评审过程都有记录
- 可以审计评审决策
- 便于持续改进

## 实现细节

### Python 脚本职责

Python 脚本（scan.py）只负责：
1. Git diff 分析
2. 调用图构建
3. 规则引擎扫描（Semgrep）
4. 生成扫描结果文件

**不负责**：
- AI 评审
- 误报过滤
- 修复建议生成

### Agent 系统职责

**主 Agent**：
1. 解析用户意图
2. 调用 scan.py
3. 委派子 Agent
4. 汇总评定决策
5. 输出最终报告

**子 Agent**：
1. 读取扫描结果
2. 分析代码上下文
3. 过滤误报
4. 生成修复建议
5. 返回评审结果

## 总结

通过主 Agent 委派子 Agent 来做代码评审，可以：
1. 充分利用 TRAE Agent 的 LLM 能力
2. 通过低温度参数确保严谨性和一致性
3. 避免在 Python 脚本中调用外部 LLM API
4. 实现完全离线的代码评审工具
5. 清晰的职责分离，便于维护和扩展
